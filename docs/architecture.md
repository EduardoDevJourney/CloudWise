# Architecture

Monorepo with a FastAPI backend (DDD) and a React frontend.

```
backend/     FastAPI API and DDD domain
frontend/    React 19 SPA
infra/       Pulumi programs
docs/
docker-compose.yml   local SQL Server
```

## RunOps flow

1. `POST /api/v1/runops/provision` checks the role and the naming policy, then stores the request as `PENDING`.
2. A background task runs Pulumi `up()`.
3. The request ends as `SUCCESS` (with the stack outputs) or `FAILED` (with a short error summary).
4. The frontend re-fetches `GET /api/v1/runops/requests` every few seconds while any request is still active.

## Backend subdomains

- **runops** (core): Pulumi provisioning
- **cloudwise** (supporting): costs and dashboard
- **auth** (generic): Easy Auth adapter and the users table that holds roles

## Cost data model

Cost reporting is analytical, so it uses a star schema. The operational side (users, templates,
provision requests) stays normalized.

```
dim_data ──────┐
dim_servico ───┼── fact_custo (custo, tags)
dim_assinatura ┘
```

| Table | Content |
|-------|---------|
| `dim_data` | one row per day: year, quarter, month, day, weekday, `ano_mes` |
| `dim_servico` | Azure service name and category |
| `dim_assinatura` | subscription code and name |
| `fact_custo` | one cost per day, service and subscription |

The dashboard filters and groups with SQL joins on the dimensions, so a new report only needs another
`GROUP BY`. `GET /cloudwise/dashboard?granularity=month` already groups by `dim_data.ano_mes`. The
sample data is generated by `seed_costs` (30 days, 3 services, 2 subscriptions).

Databases created before the star schema keep the old `cost_records` and `cost_dims` tables unused;
drop them with `DROP TABLE cost_records, cost_dims` if you want.

## Frontend layers

`core` → `ui` → `layouts` → `features` → `routes`

Imports only go in that direction; `eslint-plugin-boundaries` enforces it.
